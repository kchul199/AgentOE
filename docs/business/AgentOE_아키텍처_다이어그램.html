전체 시스템 아키텍처 개요

구성 요소 설명

VBGW (Voice Bridge Gateway): 음성 입력을 gRPC/WebSocket으로 수신하며, SESSION_HELLO, AUDIO_CHUNK, VAD, BARGE_IN 이벤트 처리

API Gateway & FastAPI Cluster: 요청 라우팅, 세션 FSM 관리, Policy Gate 검증, MCP 거버넌스

Data Layer: Redis는 실시간 세션 상태와 분산 Lock, Circuit Breaker 카운터 관리. MongoDB는 영구 저장소로 9개 컬렉션과 Time Series 감사 로그 보유

AI Services: Groq는 저지연 STT/LLM, Google TTS는 자연스러운 한국어 음성 합성

Admin Console: 테넌트별 설정, 정책 관리, 모니터링을 위한 React 기반 웹 인터페이스

💡 각 컴포넌트를 클릭하여 자세한 정보 확인

세션 생애주기 (FSM)

상태 설명

IDLE: 세션 초기 상태, VAD_START 신호 대기

LISTENING: 음성 수신 중, AUDIO_CHUNK 버퍼링

SPEAKING_DETECTED: 음성 끝 감지, VAD_END 대기

PROCESSING: STT 및 정책 검증 진행 중

INFERRING: LLM 추론 및 응답 생성 중

RESPONDING: TTS 음성 재생 중, BARGE_IN 감지 가능

ENDED: 세션 종료 상태

Policy Gate — 5단계 리스크 분류

G1
조회 (Query)
조건: 없음
예: 계좌 조회, 상품 정보 조회 → 항상 통과
G2
거래 (Transaction)
조건: 감시 및 로그
예: 송금 < 1,000,000원 → 로그 후 승인
G3
인증 필요
조건: 사용자 인증 검증
예: 대액 송금 → OTP 또는 2FA 요구
G4
이중 승인
조건: 관리자 2명 승인
예: 권한 변경, 설정 수정 → 감사자 2명 승인
G5
법무 검토
조건: 법무 팀 검토
예: 계약 수정, 정책 변경 → 항상 거부 또는 법무 검토

Policy Gate 평가 프로세스

1️⃣ 사용자 요청이 들어옴 (액션, 권한 레벨)

2️⃣ FastAPI Policy Engine이 요청 속성 분석 (risk_level, resource, user_role)

3️⃣ Policy Gate G1~G5 중 적절한 레벨 결정

4️⃣ 해당 레벨의 조건 검증:
  • G1 → 즉시 승인
  • G2 → 감시 로그 기록 후 승인
  • G3 → 사용자 인증(OTP) 요구 → Y:승인, N:거부
  • G4 → 감사자 2명 승인 대기
  • G5 → 항상 거부 또는 법무 팀으로 에스컬레이션

5️⃣ 결과 통지 및 감사 추적

멀티테넌트 아키텍처 — 완전 격리

Tenant A

🏢 예: 금융사 A

사용자: 1,000명

세션: 월 50,000건

격리: JWT tenant_id=A

Tenant B

🏢 예: 통신사 B

사용자: 2,000명

세션: 월 100,000건

격리: JWT tenant_id=B

Tenant C

🏢 예: 커머스 C

사용자: 500명

세션: 월 20,000건

격리: JWT tenant_id=C

🔒 격리 메커니즘

API Gateway (JWT Token): 각 요청의 tenant_id를 JWT에서 추출하여 FastAPI 컨텍스트에 설정. 다른 테넌트의 리소스 접근 불가

MongoDB (Collection 필터): 모든 쿼리에 {tenant_id: X} 필터 자동 추가. 인덱싱으로 성능 보장 (composite index: tenant_id + session_id)

Redis (Key Prefix): 키 구조: session:{tenant_id}:{session_id}:{field}. 별도의 namespace로 테넌트 간 데이터 혼합 방지

👤 RBAC (역할 기반 접근 제어)

8가지 역할 계층 구조:

super_admin
tenant_admin
policy_manager
operator
auditor
analyst
agent_manager
viewer

super_admin: 모든 테넌트 관리 (플랫폼 관리자만)

tenant_admin: 자신 테넌트의 모든 설정 관리

policy_manager: Policy Gate 규칙 수정

operator: 일상적 운영 (모니터링, 문제 해결)

viewer: 읽기 전용 접근

데이터 흐름 예시

요청 1 (Tenant A 사용자): GET /api/sessions?tenant_id=A → FastAPI는 JWT에서 tenant_id=A 확인 → MongoDB {tenant_id: "A"} 필터로 쿼리 → 결과만 반환

요청 2 (Tenant B 사용자): 같은 endpoint 호출 → FastAPI는 JWT에서 tenant_id=B 확인 → MongoDB {tenant_id: "B"} 필터로 쿼리 → 결과만 반환

보안: Tenant A의 악의적 사용자가 {tenant_id: "B"} 파라미터를 조작해도, JWT 토큰의 tenant_id=A가 우선되어 격리 유지
